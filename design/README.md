# 设计原型

这里放的是一个**独立的单文件 UI 原型**，用来先确认交互长什么样，再决定做什么。

它和 `progressviz` 的产品代码没有依赖关系：不读真实事件，事件是硬编码的。
它的价值是设计探索，不是功能实现。

## 它演示了两件产品还没做的事

这两条正好在 README 的「可以继续做的方向」里：

**1. 失败拦截**

不是"跑完告诉你哪里错了"，而是**在失败的那一刻停下来问你要不要继续**：

```
测试失败了 —— 现在由你决定
后面还有 5 步要跑，合计 5,900 token。你怎么选，直接决定这笔钱花不花。

[改指令重跑]  [让它自己想]  [停在这里]
```

选「改指令重跑」会替换掉默认路径的后续步骤。这是"人机协作"和"事后看日志"的分界线。

**2. 成本归因**

跑完展示每一步花了多少 token，回答"钱花在哪"：

> 读文件 + 跑测试 = 3,800 token，是模型思考的 2.9 倍。
> 真正该优化的是这里，不是让模型少想。

这个结论只有可视化之后才看得见——也成了这个工具存在的理由之一。

## 为什么不直接做成产品

因为它是假的：

- 事件是写死的，token 数是估的
- 「改指令重跑」插入的是预置事件，不是真的改 prompt
- 没有真实的事件流、没有上游

产品版本（`progressviz`）先把数据链路做真：真代理、真解析、真落盘。
UI 交互等数据稳定了再搬过去，比一开始就做个精致的假的更有价值。

## 验证

`ui_test.py` 用 headless Edge 灌驱动脚本（自动点按钮），dump DOM 后断言结构。
7 个用例 29 条断言：

```bash
python design/ui_test.py
```

需要 Windows + Edge，所以没有进 CI。

它抓到过一个真 bug：人工分支的 `splice(i + 1, 2, ...)` 写错时，
默认路径没被替换，步骤从 11 变 13 —— 截图完全看不出来。

## 配色

v2 是深色终端风，实测画面平均亮度 30.6/255，太压抑。
v3 换成亮色为主：平均亮度 239/255，深色保留为可选主题（右上角 ◐）。

背景用 `#eaf0f9` 而不是纯白，是因为白卡片放纯白背景上会糊成一片。
